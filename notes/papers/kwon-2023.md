# Kwon et al. 2023 — Efficient Memory Management for LLM Serving with PagedAttention

W. Kwon, Z. Li, S. Zhuang, Y. Sheng, L. Zheng, C. H. Yu, J. E. Gonzalez, H. Zhang,
I. Stoica. SOSP 2023. doi:10.1145/3600006.3613165 · `papers/2309.06180v1.pdf`
Owner: Valeria

## In short

The paper introduces vLLM. Serving throughput is limited by how many requests
fit in GPU memory, and the KV cache takes most of the free memory. Older systems
reserved one contiguous chunk per request at maximum length, which wasted most
of that memory. PagedAttention stores the KV cache in small fixed-size blocks,
like OS memory pages. This removes almost all of the waste and lets requests
share blocks.

## Setup

- OPT-13B/66B/175B and LLaMA-13B on A100 GPUs (Google Cloud).
- Workloads: ShareGPT (long chats) and Alpaca (short instructions), with Poisson
  arrivals at different request rates.
- Baselines: FasterTransformer, plus three variants of Orca they re-implemented.
- Metric: *normalised latency* (s/token) vs request rate, i.e. throughput at
  equal latency. **Energy is not measured.**

## Key findings

1. **The KV cache is large.** OPT-13B needs about 800 KB per token, so one
   2048-token sequence takes about 1.6 GB (§3). On an A100-40GB, weights take
   65 % of memory and the KV cache about 30 % (Fig. 1).
2. **Older systems waste most KV memory.** Only 20.4–38.2 % of it holds real
   token states; in vLLM it is 96.3 % (Fig. 2).
3. **2–4× throughput at the same latency** compared to Orca and
   FasterTransformer. The gain is largest for long sequences and for parallel
   sampling or beam search (§6).
4. **Blocks can be shared** across sequences with copy-on-write: 6–30 % memory
   saved for parallel sampling and 37–66 % for beam search. A shared prompt
   prefix is computed once (§4.4, §6.3–6.4). In the paper, shared prefixes are
   *predefined by the provider*. Automatic prefix caching (`enable_prefix_caching`)
   came in later vLLM versions (`--enable-prefix-caching`; vLLM docs, checked
   2026-11-17).
5. **When memory runs out, requests are preempted.** Their KV is either
   swapped to CPU RAM or recomputed later. Recomputation overhead never
   exceeds 20 % of swapping's latency, and both are comparable for block sizes 16–64
   (§7.3). The default block size is 16 tokens.
6. **In their chatbot experiment they deliberately do *not* keep the KV cache
   between conversation rounds**, "as doing this would occupy the space for
   other requests" (§6.5). Prompts are cut to the last 1024 tokens.

## Limitations

- Throughput and latency only; no energy, no quality (the method is exact, so
  outputs are not supposed to change).
- Older models without grouped-query attention, which have much larger KV per
  token than current ones.
- Prefix sharing is shown for few-shot prompts, not for growing chat histories.

## What it means for our project

- This is the mechanism behind our "KV cache is a limited resource" premise.
  Memory decides how many requests run at once, and that drives
  energy per request.
- Finding 6 is our trade-off in one sentence. Keeping a conversation's cache
  between turns saves recomputation but takes memory from other users. This is
  why we want a concurrent-users condition next to the single-user one.
- Block granularity matters for our context strategies. A cache hit needs
  identical full 16-token blocks from the start, so any change early in the
  prompt invalidates everything after it.
- On a 16 GB RTX 4080 a 3–4B model in bf16 takes about 6–8 GB, which leaves
  roughly 7–9 GB for KV. Memory pressure will show up at realistic conversation
  lengths and user counts. [rough estimate — compute per model]
